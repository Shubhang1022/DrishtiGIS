## 1. Purpose and Scope

This spec covers the foundational work required before the DrishtiGIS application can demonstrate its primary SIH demo path. It does not implement the full application. It establishes:

- The project repository structure and toolchain
- The frontend project foundation (Next.js, TypeScript, Tailwind, shadcn/ui, MapLibre, Anime.js)
- The backend project foundation (FastAPI, project structure, no full AI pipeline yet)
- The database schema foundation (PostgreSQL/PostGIS-compatible, Supabase-hosted for prototype)
- The Bhopal UAV data preparation pipeline (validation → mosaic → web tiles)
- The OSM data extraction pipeline (Bhopal-area subset only, from the India PBF)
- The demo data architecture (isolated, clearly labeled, honest about what it is)
- The `.gitignore` and environment variable conventions
- Initial verification and testing

This spec does NOT cover:
- Full UI implementation (landing page, map page, property panel, assistant, reports)
- Full AI inference pipeline (YOLO, SAM2.1)
- AWS GPU infrastructure
- Production-scale cadastral database
- Government authentication
- Real-time processing

## 3. Data Reality Statement

The following represents the truthful current state of available data assets. This statement must be reflected throughout the implementation — in comments, data files, UI labels, and database records.

### 3.1 What is REAL and VERIFIED

| Asset | Description | Status |
|---|---|---|
| 30 Bhopal TIFF tiles | True GeoTIFFs, EPSG:32643, RGB, 2.17 cm/pixel, ~1.0 km × 88 m footprint | REAL — raw, unprocessed |
| India OSM PBF | 1.706 GB valid PBF, Sept 5 2026 extract | REAL — too large for browser, requires server-side extraction |
| 5 Cartosat DEMs | 30m DEMs for Delhi, Lucknow, Mumbai, Prayagraj, Nellore/AP | REAL — but cover NONE of Bhopal |
| 6 OSM water-amenity GeoJSONs | Drinking water points for UP, Bihar, Maharashtra, TN, J&K, Delhi | REAL — OSM ODbL, point data only, no Bhopal |
| European Mapsforge ZIP | Mapsforge map for Germany/Czech region | REAL — geographically irrelevant |

### 3.2 What is MISSING and Must NOT be Fabricated

| Missing Asset | Handling |
|---|---|
| Bhopal cadastral/parcel boundaries | Must be sourced from government data OR created as clearly-labeled DEMO_DATA_PROTOTYPE_ONLY records |
| AI feature detection output (buildings, roads, trees, water) | Must be generated by actual model inference OR created as clearly-labeled AI_DERIVED_DEMO records |
| Historical Bhopal imagery (second time epoch) | Does not exist — must NOT be fabricated. Feature must be deferred or clearly shown as "not available for this dataset" |
| Bhopal DEM/DSM | Does not exist in current dataset — terrain features deferred |
| Discrepancy records | Cannot exist without parcel + AI feature data — deferred accordingly |
| Bhopal OSM buildings/roads | Can be extracted from India PBF using osmium-tool |

### 3.3 Data Classification System

Every piece of data used in this project must carry one of the following classifications:

| Classification | Meaning |
|---|---|
| `OFFICIAL_REFERENCE` | Authoritative government cadastral/survey data |
| `AI_DERIVED` | Output from an AI model — labeled with model name and confidence |
| `OSM_OPENSTREETMAP` | From OpenStreetMap, ODbL licensed, not authoritative cadastral data |
| `DEMO_DATA_PROTOTYPE_ONLY` | Created specifically for demonstration — never authoritative, clearly labeled |
| `RAW_RASTER_UAV` | Original unprocessed UAV imagery |
| `PROCESSED_RASTER` | Derived from RAW_RASTER_UAV via documented pipeline |

## 5. Frontend Foundation Requirements

### REQ-FE-01
The frontend must be a Next.js 14+ project using the App Router, TypeScript, and Tailwind CSS, initialized in the `drishtigis/` subdirectory.

### REQ-FE-02
The project must use `shadcn/ui` as the component library foundation. All component primitives must come from shadcn/ui before any custom component is written.

### REQ-FE-03
MapLibre GL JS must be integrated as a client-only dependency. The map component must be wrapped with `next/dynamic` and `{ ssr: false }` to prevent SSR errors. No map rendering must occur server-side.

- Micro interactions: 120–180ms
- Normal transitions: 200–300ms
- Map transitions: 400–700ms
- Major transitions: 500–800ms
- All animations must respect `prefers-reduced-motion`

### REQ-FE-05
The design token system must be configured in Tailwind CSS following the visual language from `DOC/PRD.md §4` and `DOC/requirements.md §5.1`:
- Primary background: warm cream / soft beige
- Accent: deep forest green, muted olive, warm ochre/gold
- Text: charcoal, soft gray
- No purple, no neon, no cyberpunk aesthetics

### REQ-FE-06
Two typography roles must be established as CSS custom properties and Tailwind font families:
- `font-display`: editorial serif typeface (for headlines and hero text)
- `font-ui`: modern clean sans-serif (for interface, forms, map controls, body)

### REQ-FE-07
The project must compile without TypeScript errors and without critical console errors on initial startup.

### REQ-FE-08

### REQ-FE-09
A minimal MapLibre test page must render at `/app/map` showing:

- This validates the MapLibre integration before building the full map UI

### REQ-FE-10
Environment variables must be managed via `.env.local` (gitignored). A `.env.example` file must be committed listing all required keys without values.

## 7. Database Foundation Requirements

### REQ-DB-01
The database must be PostgreSQL with the PostGIS extension. For the prototype, Supabase (hosted PostgreSQL + PostGIS) is the target, but the schema and connection code must remain portable — no Supabase-specific features that cannot be replaced with a self-hosted PostGIS instance.

### REQ-DB-02
The database schema must implement the entities defined in `DOC/requirements.md §34–39` and `DOC/PRD.md §26`:

**`users`**
```
id            uuid PRIMARY KEY DEFAULT gen_random_uuid()
email         text UNIQUE NOT NULL
name          text
role          text NOT NULL DEFAULT 'user'  -- 'user' | 'admin'
created_at    timestamptz DEFAULT now()
updated_at    timestamptz DEFAULT now()
```

**`datasets`**
```
id            uuid PRIMARY KEY DEFAULT gen_random_uuid()
name          text NOT NULL
location      text
dataset_type  text NOT NULL  -- 'orthomosaic' | 'dsm' | 'cadastral_gis' | 'other'
source        text NOT NULL  -- data classification enum
file_path     text
crs           text
bounds        geometry(Polygon, 4326)
resolution_m  numeric
status        text NOT NULL DEFAULT 'uploaded'
created_at    timestamptz DEFAULT now()
updated_at    timestamptz DEFAULT now()
```

**`parcels`**
```
id            uuid PRIMARY KEY DEFAULT gen_random_uuid()
property_id   text UNIQUE
plot_number   text
survey_number text
area_m2       numeric
land_type     text
geometry      geometry(MultiPolygon, 4326)
source        text NOT NULL  -- data classification enum
dataset_id    uuid REFERENCES datasets(id)
created_at    timestamptz DEFAULT now()
updated_at    timestamptz DEFAULT now()
```

**`properties`**
```
id            uuid PRIMARY KEY DEFAULT gen_random_uuid()
parcel_id     uuid REFERENCES parcels(id)
property_id   text UNIQUE
address       text
city          text NOT NULL
state         text NOT NULL
land_type     text
status        text
source        text NOT NULL
created_at    timestamptz DEFAULT now()
updated_at    timestamptz DEFAULT now()
```

**`ai_features`**
```
id            uuid PRIMARY KEY DEFAULT gen_random_uuid()
dataset_id    uuid REFERENCES datasets(id)
feature_type  text NOT NULL  -- 'building' | 'road' | 'tree' | 'water'
confidence    numeric CHECK (confidence BETWEEN 0 AND 1)
area_m2       numeric
geometry      geometry(MultiPolygon, 4326)
model         text
model_version text
source        text NOT NULL  -- always 'AI_DERIVED'
created_at    timestamptz DEFAULT now()
```

**`discrepancies`**
```
id                uuid PRIMARY KEY DEFAULT gen_random_uuid()
parcel_id         uuid REFERENCES parcels(id)
feature_id        uuid REFERENCES ai_features(id)
type              text NOT NULL  -- 'area_mismatch' | 'boundary_mismatch' | 'new_structure' | 'other'
official_value    numeric
ai_value          numeric
difference        numeric
difference_pct    numeric
severity          text  -- 'low' | 'medium' | 'high'
status            text DEFAULT 'pending_review'
created_at        timestamptz DEFAULT now()
```

**`processing_jobs`**
```
id            uuid PRIMARY KEY DEFAULT gen_random_uuid()
dataset_id    uuid REFERENCES datasets(id)
status        text NOT NULL DEFAULT 'queued'  -- queued|preparing|processing|analyzing|ready_for_review|published|failed
progress      integer CHECK (progress BETWEEN 0 AND 100)
started_at    timestamptz
completed_at  timestamptz
error         text
result        jsonb
created_at    timestamptz DEFAULT now()
updated_at    timestamptz DEFAULT now()
```

**`historical_snapshots`**
```
id              uuid PRIMARY KEY DEFAULT gen_random_uuid()
property_id     uuid REFERENCES properties(id)
dataset_id      uuid REFERENCES datasets(id)
captured_at     timestamptz NOT NULL
imagery_source  text NOT NULL
geometry        geometry(MultiPolygon, 4326)
change_type     text  -- NULLABLE: 'new_structure' | 'boundary_change' | 'demolition' | 'land_use_change' | NULL
                --
                -- NULL means: no historical change classification is available because
                -- real multi-temporal imagery is not available for the prototype dataset.
                -- NULL is the correct value for the prototype seed record.
                -- Do NOT fabricate a change_type value when no real second epoch exists.
confidence      numeric CHECK (confidence BETWEEN 0 AND 1)
source          text NOT NULL
created_at      timestamptz DEFAULT now()
```

### REQ-DB-03
All geometry columns must use SRID 4326 (WGS84 geographic). Input data in other CRS (e.g., EPSG:32643 from the UAV tiles) must be explicitly reprojected before storage.

### REQ-DB-04
Spatial indexes must be created on all geometry columns using `GIST`.

### REQ-DB-05
The `source` field on every entity must use the data classification values defined in §3.3. Application code must enforce this.

### REQ-DB-06
Alembic must be configured for migrations. The initial migration must create all tables and spatial indexes.

### REQ-DB-07
A database seed script must insert the demo dataset and demo parcel records. The seed script must be clearly labeled and must NOT be run in production.

## 8. Bhopal Data Preparation Requirements

### REQ-DATA-01
Before any processing, all 30 raw Bhopal TIFF tiles must be formally validated. The validation script must check and report:
- File readability
- TIFF format confirmation
- CRS (expected: EPSG:32643)
- Pixel resolution (expected: ~0.02171 m/pixel)
- Dimensions (expected: 2048×2048)
- Band count (expected: 3 RGB)
- Bit depth (expected: 8-bit)
- Bounding box in both EPSG:32643 and EPSG:4326
- Presence of NoData values and percentage
- JPEG compression confirmation
- Tile overlap / adjacency analysis

Validation must produce a JSON report saved to `data/processed/bhopal_validation_report.json`.

### REQ-DATA-02
The processing pipeline must preserve ALL original files in `Dataset/Drone-Images/BHOPAL/`. Raw files must be read-only inputs. No script may write to that directory.

### REQ-DATA-03
A mosaic must be built from all 30 tiles using GDAL's virtual raster format:
- Output: `data/processed/bhopal_mosaic.vrt` (virtual raster — no new pixel data written, references originals)
- Tile overlap handling: `gdalbuildvrt` by default uses a **last-file-wins** strategy for overlapping pixels (the last file listed covers an overlapping area). This is the only overlap behavior reliably supported by `gdalbuildvrt` without additional tooling. The implementation MUST:
  - Document the chosen overlap behavior in `pipeline.log` and in `scripts/README.md`
  - Verify visually that the mosaic has no visible seam artefacts after tiling
  - NOT claim "blend" or "average" overlap unless a blending step (e.g., via `gdalwarp -r average`) is explicitly added and verified
- The VRT itself does not perform blending — blending, if desired, would require a separate `gdalwarp` step that must be documented and implemented as a distinct pipeline stage

### REQ-DATA-04
A Cloud Optimized GeoTIFF (COG) must be created from the VRT mosaic:
- Output: `data/processed/bhopal_cog.tif`
- CRS: EPSG:32643 (preserve source CRS)
- Compression: JPEG (matching source) or LZW
- Overview levels must be generated (for MapLibre efficient loading)
- Format must be COG-compliant (verified with `gdal_info --checksum` or equivalent)

### REQ-DATA-05
An XYZ raster tile pyramid must be generated from the COG for MapLibre consumption:
- Output directory: `data/processed/tiles/bhopal/{z}/{x}/{y}.png`
- Source CRS: reproject from EPSG:32643 to EPSG:3857 (Web Mercator, required by MapLibre default tile scheme)
- Zoom levels: 18 to 22 (appropriate for 2 cm/pixel imagery)
- Tile format: PNG (lossless) or JPEG (smaller, acceptable for imagery)
- The tile directory must be gitignored (too large for Git)

### REQ-DATA-06
A bounding box GeoJSON for the Bhopal dataset coverage must be generated:
- Output: `data/processed/bhopal_bounds.geojson`
- CRS: EPSG:4326
- This GeoJSON represents the actual imagery coverage, not a city-level administrative boundary
- It must be labeled with `"source": "PROCESSED_RASTER"` and `"dataset": "Bhopal UAV Prototype"`

### REQ-DATA-07
All processing scripts must:
- Run inside the dedicated GIS environment defined in REQ-DATA-09, NOT in the main application Python environment
- Use Python with rasterio and/or GDAL (available only in the GIS environment)
- Include error handling and meaningful error messages
- Be idempotent (safe to re-run — skip steps if output already exists)
- Log all operations to `data/processed/pipeline.log`
- Never silently discard CRS information

### REQ-DATA-08
If GDAL CLI tools are not installed or not on the system PATH, the validation script must detect this and print clear installation instructions rather than crashing silently. The script must fall back to Pillow-only validation (already proven in the audit phase) if rasterio/GDAL is unavailable, and indicate which checks were skipped.

### REQ-DATA-09 — GIS Environment Isolation
GIS dependencies (GDAL, rasterio, geopandas, shapely, pyproj, fiona, osmium/pyosmium) must be installed in a **dedicated, isolated environment** separate from both:
- The system-wide Python installation (Python 3.14 with existing packages)
- The `backend/` application environment

Rationale: GDAL and rasterio have complex binary dependency chains. Installing them into the global Python environment risks breaking the existing fastapi/uvicorn/sqlalchemy/torch installation.

The dedicated GIS environment must be documented in `scripts/README.md` with exact setup instructions. Pipeline scripts must include a comment at the top identifying the required environment:
```python
# ENVIRONMENT: drishtigis-gis (conda) or OSGeo4W Python shell
# Do NOT run in the main application Python environment.
```

Acceptable isolation options (choose one and document it):
- **conda environment** named `drishtigis-gis`: `conda create -n drishtigis-gis python=3.11`
- **OSGeo4W shell** (Windows): provides GDAL + Python bindings without touching system Python
- **venv inside scripts/**: `python -m venv scripts/.gis-env` with pip-installed rasterio/GDAL wheels

The `scripts/README.md` must state which option was chosen and how to activate it before running any pipeline script.

## 9. OSM Data Extraction Requirements

### REQ-OSM-01
The India OSM PBF (`Dataset/Drone-Images/india-260905.osm.pbf`) must NEVER be loaded into the browser. All extraction must happen server-side or in preparation scripts.

### REQ-OSM-02
A Bhopal-area OSM extraction script must produce a subset GeoJSON using the Bhopal UAV coverage bounding box plus a 2 km buffer:
- Approximate bbox: `77.38°E, 23.24°N, 77.44°E, 23.27°N` (buffered beyond the 1 km UAV strip)
- Tool: `osmium extract` (preferred) or `pyosmium` (Python)
- Output formats:
  - `data/osm/bhopal-buildings.geojson` — building polygons
  - `data/osm/bhopal-roads.geojson` — road linestrings
  - `data/osm/bhopal-waterways.geojson` — waterway linestrings and polygons
  - `data/osm/bhopal-landuse.geojson` — land use polygons

### REQ-OSM-03
All extracted OSM GeoJSON files must include:
- A `"_source": "OSM_OPENSTREETMAP"` property on each feature
- An `"_attribution": "© OpenStreetMap contributors, ODbL"` property on each feature
- OSM data must NEVER be labeled as authoritative cadastral data in the application

### REQ-OSM-04
If osmium-tool is not installed, the extraction script must detect this and print clear installation instructions. It must NOT attempt to parse the 1.71 GB PBF directly in Python without streaming.

### REQ-OSM-05
The extraction script must verify the output file sizes are reasonable (buildings GeoJSON < 10 MB for the target bbox). If the output is unexpectedly large, it must warn and offer to re-run with a tighter bbox.

## 10. Demo Data Architecture Requirements

### REQ-DEMO-01
An isolated demo data package must be created at `drishtigis/lib/demo-data/`. This directory contains only data that is explicitly labeled as prototype demonstration data. It must NEVER contain data presented as authoritative government records.

### REQ-DEMO-02
The demo data package must include:

**`bhopal-parcels.geojson`** — 3 to 5 demo parcel polygons:
- Geometries MUST fall within the actual Bhopal TIFF coverage area (bounds: 23.2557°–23.2567°N, 77.413°–77.423°E)
- Each feature MUST have `"_source": "DEMO_DATA_PROTOTYPE_ONLY"` and `"_disclaimer": "This is prototype demo data, not official cadastral data"`
- Properties: `id`, `property_id`, `plot_number`, `survey_number`, `area_m2`, `land_type`, `status`, `city`, `_source`, `_disclaimer`
- Property IDs must use a `DRS-BPL-` prefix (Bhopal, not Lucknow or any other city)
- Area values must be plausible for Bhopal residential plots (300–1500 m²)

**`bhopal-ai-features.geojson`** — demo AI detection results:
- Building polygons that MAY partially extend outside the corresponding demo parcel boundary — this is the spatially correct representation of a discrepancy. A real AI model detects a physical structure footprint; that footprint may exceed the recorded parcel polygon. The area excess must be expressed geometrically (polygon overlap/extension), not merely as a numeric difference in the discrepancy record.
- Each feature MUST have `"_source": "AI_DERIVED_DEMO"`, `"model": "demo_placeholder"`, `"confidence": <value 0–1>`
- Properties: `id`, `feature_type`, `confidence`, `area_m2`, `model`, `model_version`, `dataset`, `_source`
- The `area_m2` field must reflect the actual area of the AI polygon geometry — it must NOT be set to match the parcel area
- Must be visually distinct from the parcel boundaries when rendered on the map

**`bhopal-discrepancies.json`** — demo discrepancy records:
- Each record links a demo parcel ID to a demo AI feature ID
- Must show a plausible area difference (e.g., recorded 450 m², AI detected 487 m², difference +37 m², +8.2%)
- Language: "Potential discrepancy — requires verification" — NEVER "illegal construction" or "fraud"
- Must include `"_source": "DEMO_DATA_PROTOTYPE_ONLY"`

**`properties.json`** — demo property records:
- One record per parcel
- City field: `"Bhopal"` — NEVER another city name
- All records have `"_source": "DEMO_DATA_PROTOTYPE_ONLY"` and `"_datasetLabel": "Prototype Dataset — Bhopal"`

**`index.ts`** — TypeScript module that exports all demo data with full type annotations

### REQ-DEMO-03
A TypeScript type definition file `drishtigis/lib/demo-data/types.ts` must define interfaces for all demo data structures, including a `DataSource` enum with all classification values from §3.3.

### REQ-DEMO-04
The demo data must NEVER be imported directly into production API routes that serve real data. It must only be used in:
- Frontend demo-mode rendering
- Placeholder API responses clearly marked as demo

### REQ-DEMO-05
Historical imagery demo data must NOT be fabricated. The `historical_snapshots` table may be seeded with a single record that clearly states `"imagery_source": "DEMO_DATA_PROTOTYPE_ONLY"` and `"change_type": null`. The historical comparison UI must display "Historical imagery not available for this prototype dataset" until real multi-temporal data is acquired.

## 12. Testing and Verification Requirements

### REQ-TEST-01
After project initialization, the following must pass:
- `npm run build` in `drishtigis/` — zero TypeScript errors
- `npm run lint` — zero lint errors
- All route pages render without 500 errors in development mode

### REQ-TEST-02
After data preparation:
- Validation script must report all 30 tiles as valid GeoTIFFs
- COG must open with correct bounds and CRS using rasterio or GDAL
- XYZ tile verification must confirm ALL of the following (file existence alone is not sufficient):
  1. Tile files exist at zoom levels 18–21 in the output directory
  2. The XYZ tile coordinates at zoom 18 that correspond to Bhopal (~23.256°N, 77.417°E) are computed and verified to exist — these are the specific tile grid cells that MUST be populated
  3. At least 3 tiles at zoom level 18 are non-empty (file size > 500 bytes, not a blank/transparent PNG)
  4. A sample tile at zoom 18 is opened as an image and confirmed to contain non-uniform pixel values (i.e., actual imagery, not a solid color or transparent fill)
  5. The tile directory structure follows the expected EPSG:3857 XYZ scheme: `{z}/{x}/{y}.png` with x/y values consistent with the Bhopal bounding box at the relevant zoom levels
- `bhopal_bounds.geojson` must load in a browser-based GeoJSON viewer showing coverage in Bhopal
